Как работают базы данных

Интерактивный тренажёр — потрогай таблицы, связи, документы и графы руками

Модель данных — одно из главных понятий теории БД. Она задаёт, как данные организованы и как к ним обращаться. Моделей несколько — вот основные. (NoSQL = Not Only SQL — «не только SQL», а не «без SQL».)

TREE иерархическая модель — потрогай дерево

Самая ранняя модель: данные — это дерево. У каждого узла ровно один родитель и сколько угодно детей. Кликай ветки, чтобы свернуть или развернуть.

Плюс: идеально для древовидных данных — каталог, файлы, оргструктура. Минус: у узла один родитель — нельзя выразить «товар сразу в двух категориях» (это уже многие-ко-многим → реляционная или графовая модель). Так устроены файловая система, XML/JSON, IBM IMS.

ZOO основные модели данных

Одни и те же товары и заказы можно уложить совершенно по-разному. У четырёх моделей есть отдельная вкладка «потрогать» — жми кнопку.

Иерархическая

Дерево: у узла один родитель, много детей.
Магазин ▸ Электроника ▸ 🎧
Где: файловая система, XML, IBM IMS

Реляционная

Таблицы (строки × колонки), связи по ключам.
[ users ] —id→ [ orders ]
Где: PostgreSQL, MySQL, Oracle

Документоориентированная

Вложенные JSON-документы, гибкая схема.
{ order: 1, items: [ … ] }
Где: MongoDB, Couchbase

Ключ-значение

Словарь: по ключу — значение, мгновенно.
"cart:anna" → [ 🎧, чехол ]
Где: Redis, DynamoDB

Графовая

Узлы и рёбра; связи — полноценные объекты.
(Анна) —дружит— (Борис)
Где: Neo4j, ArangoDB

Колоночная (wide-column)

Данные по семействам колонок; масштаб на запись.
row → { колонка: значение, … }
Где: Cassandra, HBase, ScyllaDB
И это не всё: есть ещё объектная, временных рядов (time-series), векторная (для AI-поиска по смыслу) и другие. Полный «зоопарк» движков — на вкладке «Когда что».

WIDE-COLUMN колоночная — потрогай

Представь гигантский вложенный словарь: строка (rowkey) → семейства колонок → колонки → значение. Главное — у каждой строки свой набор колонок (гибко), а отсутствующие колонки не занимают места (разреженность). Так устроены Cassandra, HBase.

У разных строк — разные колонки. Переключи «по колонкам» — увидишь, как это лежит на диске.

3 УРОВНЯ от бизнеса к базе: концептуальный → логический → физический

ИТОГ одна логика — разные реализации

Концептуальная и логическая схемы не зависят от СУБД — это про бизнес и структуру. Физическая у PostgreSQL, MongoDB или ClickHouse будет разной. Сначала думаем ЧТО и КАК, и только потом ЧЕМ.

Концептуальная — сущности и связи на языке бизнеса. Отвечает: ЧТО моделируем.
Логическая — таблицы, атрибуты, ключи, нормализация. Отвечает: КАК организуем. Без привязки к СУБД.
Физическая — типы данных, индексы, DDL под конкретную СУБД. Отвечает: ЧЕМ реализуем.

Реляционная база — это таблицы, как листы в Excel. У каждой таблицы заранее задана схема: список колонок, у каждой колонки — строгий тип. Строки нельзя хранить как попало — за этим следят ограничения (constraints). Ниже — настоящий интернет-магазин из двух таблиц. Попробуй сломать правила и посмотри, что ответит база.

TABLE users — пользователи

Каждая строка — один человек. Колонка id — первичный ключ (PRIMARY KEY): уникальный номер строки. По нему на пользователя ссылаются другие таблицы.

Заполнить пример:
Заполни поля и нажми «Добавить строку». Или ткни готовый пример — и посмотри реакцию базы.
PK первичный ключ — уникален, не пустой UNIQUE значение не повторяется NOT NULL нельзя оставить пустым CHECK проверка условия FK ссылка на другую таблицу

TABLE orders — заказы

Заказ принадлежит пользователю. Колонка user_id — внешний ключ (FOREIGN KEY): она обязана ссылаться на существующий users.id. База не даст создать заказ «ничей» и не даст удалить пользователя, у которого есть заказы — это целостность данных.

Заказ ссылается на пользователя через user_id.

JOIN соединяем таблицы запросом

Данные лежат в разных таблицах без дублирования. Чтобы увидеть «заказ + кто его сделал», база соединяет таблицы по ключу в момент запроса — это операция JOIN. Имя пользователя хранится только один раз, в users.

SELECT o.id, u.name, u.email, o.product, o.amount
FROM orders o JOIN users u ON o.user_id = u.id;

Данные хранят, чтобы их доставать. Базовые операции запроса — фильтр, сортировка, уникальные, группировка и агрегаты. У каждой есть свои особенности, на которых часто спотыкаются новички. Переключай операции и смотри, как исходная таблица sales превращается в результат — и какие у каждой операции подводные камни.

ОПЕРАЦИИ запросы: было → стало

ПОРЯДОК в каком порядке БД выполняет запрос

Пишем запрос в одном порядке, а СУБД выполняет в другом. Именно поэтому в WHERE нельзя фильтровать агрегаты (он идёт до GROUP BY), а в ORDER BY можно использовать алиасы из SELECT (он идёт после).

1. FROM
берём таблицы
2. WHERE
фильтр строк
3. GROUP BY
группировка
4. HAVING
фильтр групп
5. SELECT
выбор колонок
6. ORDER BY
сортировка
7. LIMIT
срез N строк
Запомни этот порядок — он объясняет большинство «странностей» SQL. Алиасы из SELECT видны только в ORDER BY; агрегаты появляются лишь начиная с HAVING.

JOIN соединяет строки двух таблиц по ключу. Тип JOIN решает, что делать со строками без пары. Возьмём users и orders: у Веры нет заказов, а заказ #103 ссылается на несуществующего пользователя (id 5). Переключай тип — смотри, кто попадёт в результат.

КАК УСТРОЕН индекс изнутри — на картинке

      
Индекс — это отдельная отсортированная структура со значениями колонки и указателями на строки. Как алфавитный указатель в конце книги: не читаешь всю книгу — открываешь указатель на нужное слово и сразу прыгаешь на страницу. Сами данные лежат в таблице как попало, а индекс лишь знает, «где искать».

      
      
Значения в индексе идут по порядку, поэтому нужное находится быстро; стрелка ведёт к самой строке в таблице.


      
Внутри индекс — это B-дерево. Поиск идёт сверху вниз: на каждом уровне сравниваешь значение с ключами узла и уходишь в нужную ветку, отбрасывая остальные. Кликни любое число в листе — подсвечу путь.

      
      
Кликни число внизу — подсветится путь от корня к нему.

      
Почему быстро: дерево из ~3–4 уровней вмещает миллионы строк, а поиск — это всего ~3–4 шага вместо перебора всех строк. Отсюда и берётся log n.

TRADE-OFF почему не навесить индекс на всё подряд

      

        
Ускоряет чтение
Поиск и сортировка по индексированной колонке — в разы быстрее: примерно log(n) шагов вместо n.

        
Замедляет запись
При каждом INSERT/UPDATE база обязана обновлять ещё и индекс. Много индексов → медленные вставки.

        
Занимает место
Индекс — отдельная структура на диске. И он бесполезен, если искать по колонке, которой в нём нет.

      

      
Правило: индексируй колонки, по которым часто ищешь, соединяешь (JOIN) или сортируешь — обычно это внешние ключи и поля из условий WHERE. А PRIMARY KEY и UNIQUE создают индекс автоматически.

    


    

      
ВИДОВ МНОГО каких бывают индексы

      
По умолчанию почти везде B-tree, но под особые задачи есть ещё десяток видов. Знать все наизусть не нужно — достаточно понимать, что и для чего. Категории — это три разные «оси», а не взаимоисключающие типы.


      
По структуре данных (как устроен сам индекс)

      

        
B-tree (B+-дерево)
по умолчанию везде. Сравнения =, <, >, BETWEEN, ORDER BY и префикс LIKE 'абв%'. Универсал.

        
Hash
хеш от значения. Только точное равенство (=), зато очень быстро. Без диапазонов и сортировки.

        
Bitmap
битовая маска строк на каждое значение. Малая кардинальность (пол, статус, регион), аналитика с AND/OR. Классика хранилищ (Oracle); в PG — bitmap-сканы на лету.

        
GIN (инвертированный)
когда в одной ячейке много значений: полнотекстовый поиск, массивы, JSONB, теги.

        
GiST
обобщённое дерево для сложных типов: геоданные (пересечения, «ближайшие»), диапазоны, полнотекст. Основа PostGIS.

        
BRIN
хранит только min/max по блокам. Компактный, для огромных таблиц с физическим порядком (time-series по дате).

        
R-tree / SP-GiST
специализированные — для пространственных и иерархических данных.

      


      
По физической организации

      

        
Кластерный
задаёт физический порядок строк на диске; строки лежат прямо в листьях. Только один на таблицу (PK в SQL Server, InnoDB). В PostgreSQL истинного нет (есть разовый CLUSTER).

        
Некластерный (вторичный)
отдельная структура: ключ + ссылка на строку. Их может быть много на одной таблице.

      


      
По логическим свойствам

      

        
Уникальный
запрещает дубликаты значений — основа PRIMARY KEY и UNIQUE-ограничений.

        
Составной (multi-column)
по нескольким столбцам. Важен порядок: индекс (A, B) работает для условий по A и по A+B, но не по одному B.

        
Покрывающий (covering)
содержит все нужные запросу столбцы → к таблице обращаться не надо (index-only scan). Доп. столбцы через INCLUDE.

        
Частичный (partial)
строится только по части строк (WHERE deleted = false). Меньше по размеру, быстрее обновляется.

        
Функциональный (по выражению)
индексирует результат функции, а не столбец: LOWER(email), EXTRACT(year FROM created_at).

      


      
Один индекс может сочетать свойства сразу с нескольких осей — например, уникальный составной частичный B-tree. Структура (B-tree/Hash/…), физическая организация (кластерный/нет) и логические свойства (уникальный/составной/…) — независимы.

    


    

      
ПРИМЕРЫ CREATE INDEX для каждого типа

      
Как эти индексы выглядят в коде (синтаксис PostgreSQL). По умолчанию CREATE INDEX строит B-tree; для остальных типов указывают USING.


      
По структуре данных

      
-- B-tree (по умолчанию): =, <, >, BETWEEN, ORDER BY, LIKE 'абв%'
CREATE INDEX idx_users_email ON users (email);

-- Hash: только точное равенство (=)
CREATE INDEX idx_sessions_token ON sessions USING hash (token);

-- GIN (инвертированный): массивы, JSONB, теги, полнотекст
CREATE INDEX idx_posts_tags ON posts USING gin (tags);
CREATE INDEX idx_docs_fts   ON docs  USING gin (to_tsvector('russian', body));

-- GiST: геоданные, диапазоны (основа PostGIS)
CREATE INDEX idx_places_geom ON places USING gist (geom);

-- BRIN: огромные упорядоченные таблицы (time-series по дате)
CREATE INDEX idx_events_ts ON events USING brin (created_at);

-- SP-GiST: пространственные / иерархические данные
CREATE INDEX idx_points_loc ON points USING spgist (location);

-- Bitmap: в PostgreSQL отдельного типа нет — планировщик строит bitmap-скан сам.
-- В Oracle:  CREATE BITMAP INDEX idx_orders_status ON orders (status);


      
По физической организации

      
-- Некластерный (обычный, вторичный) — их может быть много на таблице
CREATE INDEX idx_orders_customer ON orders (customer_id);

-- Кластерный: в SQL Server — CREATE CLUSTERED INDEX ...
-- В PostgreSQL истинного нет; разовая физическая переупорядочка строк:
CLUSTER orders USING idx_orders_customer;


      
По логическим свойствам

      
-- Уникальный (основа PRIMARY KEY и UNIQUE)
CREATE UNIQUE INDEX idx_users_email ON users (email);

-- Составной: важен порядок — работает для (customer_id) и (customer_id, status),
--            но НЕ для одного status
CREATE INDEX idx_orders_cs ON orders (customer_id, status);

-- Покрывающий: доп. столбцы через INCLUDE → index-only scan (к таблице не ходим)
CREATE INDEX idx_orders_cover ON orders (customer_id) INCLUDE (amount, status);

-- Частичный: индексируем только часть строк
CREATE INDEX idx_active_users ON users (email) WHERE deleted = false;

-- Функциональный (по выражению): индекс на результат функции
CREATE INDEX idx_lower_email ON users (LOWER(email));

    


    

      
СРАБОТАЕТ? как отрабатывают логические индексы

      
Эти индексы срабатывают не на любом запросе — важно, совпадает ли запрос с индексом. Переключай тип и смотри: на каком запросе индекс используется (✓), а на каком база уходит в полный перебор (✗).

      

        
        
        
        
      

      

    

  


  
  

    
Разберём на примере PostgreSQL, что происходит «под капотом» реляционной базы — простым языком и со схемами. Четыре вещи: как выполняется запрос, как данные организованы логически, как лежат физически и что бережёт их от потери.


    

      
1 · ЗАПРОС путь SQL-запроса внутри сервера

      
Когда ты отправляешь SQL, база не выполняет его «в лоб». Сначала разбирает, потом планирует самый быстрый способ, и только затем достаёт данные.

      
      
Планировщик — ключевой момент: именно он решает, использовать индекс или читать всю таблицу. Поэтому один и тот же запрос с индексом и без — небо и земля (см. вкладку «Индексы»).

    


    

      
2 · ЛОГИКА организация: кластер → база → схема → объекты

      
Матрёшка. На сервере — кластер, в нём несколько баз. База делится на схемы — логические папки. В схемах живут объекты: таблицы, индексы, представления (views).

      

        
🖥 Кластер PostgreSQL

        

          
🗄 База данных «shop»

          

            
📂 Схема public (сюда попадают твои таблицы)

            
▦ users▦ orders🔑 idx_email👁 v_report

          

          
⚙ pg_catalog · information_schema — системные схемы

        

        
🗄 База данных «analytics»

      

      
Системные схемы: pg_catalog — служебный каталог самой базы; information_schema — стандартные представления о структуре; public — сюда по умолчанию попадают твои объекты. Схему нельзя вложить в схему.

    


    

      
3 · ФИЗИКА буферный кеш ↔ страницы 8 КБ ↔ файлы

      
На диске данные лежат в файлах, разбитых на страницы по 8 КБ (страница = заголовок + строки). Диск медленный, поэтому «горячие» страницы Postgres держит в буферном кеше в оперативной памяти. Кликай страницы на диске — увидишь, как работает кеш.

      

        
Оперативная память — буферный кеш (4 слота)

        
Диск — страницы по 8 КБ (кликай)

        
Попаданий: 0 · Промахов: 0

      

      
Кликни страницу на диске. Первый раз — промах (читаем с диска), повторно — попадание (берём из оперативки).

      
Поэтому первый запрос к данным медленнее, а повторные — быстрые: страница уже в кеше. Это же объясняет, зачем серверу БД много оперативной памяти.

    


    

      
3.5 · ДВИЖОК как строка попадает на диск (под капотом)

      
Что реально происходит при INSERT? Строка не летит сразу в файл таблицы. Движок сначала пишет в журнал, потом меняет страницу в памяти, а на диск в таблицу — позже. Жми «Дальше» и проходи путь строки по шагам.

      

      

      
Нажми «Дальше», чтобы пройти путь строки от клиента до диска.

      
Строка лежит в странице как кортеж (tuple); очень большие значения выносятся в отдельное хранилище (TOAST). «Горячий путь» записи — только WAL (диск) + буфер (RAM), поэтому COMMIT быстрый; тяжёлый сброс в файл таблицы откладывается на checkpoint.

    


    

      
4 · НАДЁЖНОСТЬ почему данные не теряются и не мешают друг другу

      

        
WAL — журнал предзаписи
Прежде чем менять данные, Postgres пишет намерение в журнал. Выключился свет — после перезапуска база доигрывает журнал и ничего не теряет.

        
MVCC — многоверсионность
При изменении строки создаётся её новая версия; кто читал раньше — видит старую. Читатели не блокируют писателей, тысячи людей работают разом.

        
Транзакции — «всё или ничего»
Группа изменений применяется целиком (COMMIT) или откатывается полностью (ROLLBACK). На этом держатся денежные переводы.

      

    

  


  
  

    
Транзакция — группа операций, которая выполняется как единое целое: либо всё, либо ничего. Это бережёт данные, когда что-то ломается посреди процесса или когда с базой работают тысячи людей разом. Гарантии транзакций описывает аббревиатура ACID.


    

      
ACID четыре гарантии

      

        
A — Atomicity (атомарность)
Все шаги применяются целиком или откатываются целиком. Половины перевода быть не может.

        
C — Consistency (согласованность)
База переходит из одного корректного состояния в другое: все ограничения (PK, FK, CHECK) соблюдены.

        
I — Isolation (изоляция)
Одновременные транзакции не мешают друг другу — как будто идут по очереди.

        
D — Durability (устойчивость)
После COMMIT данные сохранены навсегда, даже если тут же выключат свет (спасибо WAL).

      

    


    

      
A · АТОМАРНОСТЬ перевод денег — потрогай

      
Переводим 300 ₽ от Ани к Боре. Это два шага: списать у Ани, зачислить Боре. Смотри, что будет при сбое посередине — с транзакцией и без. «Всего» всегда должно быть 1500 ₽.

SQL — это не одна «куча команд», а несколько семей. Главное различие: одни команды меняют структуру базы (скелет), другие — сами данные (наполнение). Разберём, и особенно — DDL.


    

      
SQL четыре семьи команд

      

        
DDL
CREATE · ALTER · DROP
Data Definition Language — описание структуры: таблицы, колонки, индексы. Меняет «скелет» базы.

        
DML
INSERT · UPDATE · DELETE · SELECT
Data Manipulation Language — работа со строками: добавить, изменить, удалить, прочитать. Структуру не трогает.

        
DCL
GRANT · REVOKE
Data Control Language — права доступа: кому что можно.

        
TCL
BEGIN · COMMIT · ROLLBACK
Transaction Control — управление транзакциями: применить всё или откатить.

      

      
Аналогия: DDL строит и перестраивает комнаты в доме (стены, двери), а DML расставляет и двигает мебель внутри. Сначала «скелет» (DDL) — потом данные (DML).

    


    

      
DDL подробно, с примерами

      
DDL (Data Definition Language) — команды, которые определяют и меняют структуру базы. Три главные:

      

        

          
CREATE создать объект

          
CREATE TABLE users (
  id     SERIAL PRIMARY KEY,
  email  VARCHAR(255) UNIQUE NOT NULL,
  age    INTEGER CHECK (age >= 0)
);

          
Создаёт новую таблицу с колонками, типами и ограничениями. Так же создают индексы (CREATE INDEX …) и представления (CREATE VIEW …).

        

        

          
ALTER изменить существующий объект

          
ALTER TABLE users ADD COLUMN city VARCHAR(100);
ALTER TABLE users ADD CONSTRAINT uq_email UNIQUE (email);

          
Добавляет колонку или ограничение, меняет тип — таблица уже есть, мы правим её структуру.

        

        

          
DROP удалить объект целиком

          
DROP TABLE orders;

          
Удаляет таблицу вместе со всеми данными и структурой. Осторожно: это «снести комнату», а не «убрать мебель» (для строк есть DELETE из DML).

        

      

    


    

      
ТРЕНАЖЁР DDL или DML?

      
Определи для каждой команды: она меняет структуру (DDL) или данные (DML)?

      

    


    

      
КЕЙСЫ 🔩 что повесить: ограничения и индексы

      
Требование из жизни — а ты решаешь, что применить: ключ, ограничение или индекс. После ответа покажу готовый SQL и объясню, почему именно это.

      

    

  


  
  

    
Мелкие, но важные вещи, на которых спотыкаются новички: чем БД отличается от Excel, как хранить деньги, даты и картинки, что такое NULL, как внешний ключ ведёт себя при удалении и когда нормализацию нарочно нарушают.

Проще всего понять БД через знакомый Excel. База — как таблица в Excel, но «на стероидах»: для многих людей сразу, для огромных объёмов и без права на ошибку.

ФАЙЛЫ как хранить картинки и документы

      
Частый вопрос новичка: «а как засунуть картинку в базу?» Есть два пути — и почти всегда выбирают второй.

      

        
1. Прямо в базу (BLOB / bytea)
Файл лежит внутри строки как набор байт. Плюс: всё в одном месте, попадает в транзакции и бэкап. Минус: база быстро пухнет, отдавать тяжёлые файлы медленно и дорого.

        
2. Ссылка на файл (URL / путь)
Сам файл — в файловом/облачном хранилище (например, S3), а в базе только короткая ссылка-текст. Плюс: база лёгкая и быстрая, файлы раздаёт CDN. Минус: надо следить за согласованностью (удалил строку — удали и файл).

      

      
На практике: картинки и документы почти всегда хранят как ссылку + объектное хранилище. BLOB прямо в базе — только для мелких файлов или когда критична строгая транзакционность.

    


    

      
ТИПЫ данных: бери правильный

      

        
Деньги → DECIMAL / NUMERIC
никогда не float! У float 0.1 + 0.2 ≠ 0.3. Для денег — точный DECIMAL(10,2).

        
Дата/время → TIMESTAMPTZ
с таймзоной, хранить в UTC. Иначе «10:00» — это 10:00 где именно?

        
JSON → JSONB
гибкие/вложенные данные; индексируется через GIN.

        
UUID
глобально уникальный id — удобно для распределённых систем (не пересечётся, не угадать).

        
ENUM / справочник
фиксированный набор значений (статусы) вместо «магических строк».

        
BOOLEAN · INTEGER · VARCHAR(n) · TEXT
базовые. VARCHAR(n) — с лимитом длины, TEXT — без лимита.

NULL «неизвестно» и трёхзначная логика

      
NULL — это не 0 и не пустая строка, а «значение неизвестно». Поэтому сравнения с ним дают не TRUE/FALSE, а UNKNOWN. Кликай выражения — проверь.

ДЕНОРМАЛИЗАЦИЯ когда нарочно нарушают нормальную форму

      
Нормализация убирает дубли, но за это платят JOIN-ами при чтении. Иногда данные сознательно дублируют ради скорости — это денормализация (контрапункт к вкладке «Нормализация»).

      

        
Счётчик комментариев
Вместо COUNT(*) по миллионам строк при каждом показе — хранят готовое поле comments_count в посте и обновляют при добавлении.

        
Имя автора в заказе
Копируют имя покупателя в заказ, чтобы показать историю без JOIN — и «заморозить» имя на момент покупки.

        
Цена платы
Дубли надо держать в актуальном состоянии — растёт риск рассинхрона. Денормализуют точечно и осознанно.

      

      
Правило: по умолчанию нормализуй; денормализуй только когда упёрся в скорость чтения и измерил, что JOIN — узкое место. Читать быстрее ↔ писать сложнее.

    

  


  
  

    
«Нереляционные» (NoSQL) — это не одна вещь, а несколько разных подходов. Их придумали, когда жёсткие таблицы стали мешать: где-то нужна гибкость, где-то — максимальная скорость, где-то — работа со связями. Разберём три самых частых семейства на том же магазине.


    

      
DOCUMENT документная база — MongoDB

      
Данные хранятся не строками в таблицах, а документами (это по сути JSON). Один заказ — один документ, внутри которого вложены и покупатель, и список товаров. Никаких JOIN: весь заказ читается за один запрос.

Документно: весь заказ — один объект

          

          

            
          

        

      

      
Плюс: гибкая схема — можно добавить поле одному документу, не трогая остальные. Быстро читать.  Минус: данные покупателя дублируются в каждом его заказе; поменял email — придётся обновлять во многих местах.

    


    

      
KEY-VALUE ключ-значение — Redis

      
Самая простая модель — обычный словарь (Map): по ключу мгновенно достаёшь значение. Ни таблиц, ни связей, ни поиска по содержимому — зато молниеносно. На этом держатся кэш, сессии, корзины и счётчики.

      

      

        

        

        
        
      

      
SET — записать пару. GET — достать значение по ключу. Кнопка +1 у счётчика показывает атомарный INCR.

      
Доступ по ключу — O(1), мгновенно. Но нельзя спросить «покажи все корзины дороже 1000 ₽» — по значению искать нечем. Ключ знаешь — получил, не знаешь — всё.

    


    

      
GRAPH графовая база — Neo4j

      
Здесь главное — не данные, а связи между ними. Узлы — люди, рёбра — «дружит с». Связь такой же полноценный объект, как и сам человек. Вопросы «друзья друзей», «на сколько рукопожатий мы знакомы», рекомендации — решаются естественно, тогда как в таблицах это превращается в кучу JOIN.

      

        
        
        
        
        
      

      

      
Кликни человека — подсветятся его друзья. Узлы можно перетаскивать.

    

  


  
  

    
Нет «лучшей» базы — есть подходящая под задачу. Часто в одном продукте живут сразу несколько: реляционная под деньги, кэш под скорость, графовая под ленту рекомендаций.

OLTP · OLAP два режима работы с данными

      
Это уже не про тип базы, а про характер нагрузки. Одну и ту же информацию можно обрабатывать двумя очень разными способами — и под них берут разные базы.

      

        

          
OLTP — оперативная работа

          
Много коротких операций «здесь и сейчас»: оформить заказ, списать деньги, обновить профиль. Трогаем отдельные строки. Это повседневная жизнь приложения.

        

        

          
OLAP — аналитика

          
Редкие, но тяжёлые запросы по огромным объёмам: «выручка по регионам за 3 года». Читаем миллионы строк ради агрегатов, отчётов и дашбордов.

ИНФОГРАФИКА строки vs колонки: как данные лежат на диске

      
Почему аналитические (колоночные) БД так быстры на запросах вроде «сумма по колонке»? Всё дело в том, как байты лежат на диске. Выбери запрос — подсветится, сколько ячеек прочитает каждое хранилище.

      

        
        
      

      
прочитано и пригодилосьпрочитано впустуюне читалось

      
📁 Строковое (row-store): каждая строка лежит целиком подряд 

      
📊 Колоночное (column-store): каждая колонка — отдельным блоком 

      

      
Бонус колоночного: в одном блоке лежат значения одного типа (все суммы, все города) — они отлично сжимаются, и на диск ложится в разы меньше. Плата: «достать одну строку целиком» дороже — её приходится собирать из разных блоков. Отсюда правило: колоночные — под аналитику (OLAP), строковые — под операции (OLTP).

Когда одна машина перестаёт справляться, базу масштабируют. Вертикально — дать серверу больше мощи (есть потолок и дорого). Горизонтально — раскидать нагрузку по многим машинам (сложнее, но почти без потолка). Ниже три главных приёма — потрогай.


    

      
РЕПЛИКАЦИЯ копии для чтения

      
Один мастер принимает записи, они копируются на реплики. Чтения раскидываются по репликам — мастер разгружен. Жми кнопки, смотри, куда уходит нагрузка (число — сколько запросов обработал узел).

      

      

        
        
        
        
      

      
Чтения идут на реплики, записи — только на мастер.

      
Плюс: много чтений держим легко, есть резервная копия. Минус: реплика отстаёт на доли секунды (лаг) — можно прочитать чуть устаревшее.

    


    

      
ШАРДИРОВАНИЕ данные по кускам

      
Данные делят между серверами по ключу (шардами). Например, шард = id % 3. Каждый шард хранит свою часть — вместе они вмещают то, что не влезло бы в одну машину. Выбери пользователя — покажу его шард.

      

      

      
Выбери id — вычислю шард.

      
Плюс: и объём, и запись масштабируются горизонтально. Минус: запросы «по всем шардам» и JOIN между ними усложняются; ключ шардирования надо выбирать с умом.

    


    

      
ПАРТИЦИОНИРОВАНИЕ одна таблица — много секций

      
Похоже на шардирование, но внутри одной базы: большую таблицу режут на секции по диапазону (например, заказы по месяцам). Запрос за «март» читает только мартовскую секцию, а старые секции можно быстро архивировать/удалять целиком.

      

        
orders_2024_01январьсекция

        
orders_2024_02февральсекция

        
orders_2024_03мартзапрос за март — сюда

      

      
Вертикальное масштабирование — «сервер побольше». Горизонтальное (репликация / шардирование / партиции) — «серверов побольше». В крупных системах используют всё сразу.
